# Realtime 變更通知與跨裝置同步評估

日期：2026-10-21  
狀態：方案評估，未實作、未部署；本文件不代表雲端設定或 migration 已獲批准。

## 目的與評估範圍

讓使用者不必重新整理網頁，也能取得：

- 同一帳號在其他裝置新增、修改或刪除的個人資料。
- 協作者修改的共享行程內容，以及相關存取權變動。

本方案整理產品需求與 Supabase Realtime 的選型建議，
尚未針對目前專案完整檢查同步接線、資料庫異動位置或實際部署設定。
以下所稱「既有同步流程」是預期重用的方向，實作前仍需確認其涵蓋範圍。

## 結論

優先考慮：

> 私人 Broadcast 變更通知＋既有同步流程＋重連／回到前景補同步。

Realtime 只作為「資料可能已更新」的訊號，不直接取代同步協定、
持久 outbox、增量游標、版本檢查或衝突處理。
第一階段不加入 Presence，也不做逐欄位即時共同編輯。

整體複雜度預估為中等；接收通知本身不難，主要成本在頻道授權、
事件合併、同步排程、斷線恢復及草稿保護。這不是已完成程式盤點後的工時估算。

## 技術選型

| 功能 | 用途 | 適用性與取捨 |
| --- | --- | --- |
| Postgres Changes | 訂閱資料表異動 | 設定較少，適合快速起步；隨訂閱數與資料量增加有擴充限制，需確認 RLS 與刪除事件限制。 |
| Broadcast | 頻道訊息；可由資料庫 trigger 自動發送 | 建議方案。可依帳號／行程組織私人通知，但須新增觸發與 Realtime 授權設定。 |
| Presence | 在線與使用者狀態 | 暫不需要；可日後用於顯示誰正在編輯，不是資料同步、鎖定或防覆寫機制。 |

Supabase 官方目前建議以 Broadcast 訂閱資料異動，
理由為擴充性與安全性；Postgres Changes 是較簡單、設定較少的替代方案。
選用 Broadcast 不會自動保證安全，仍須正確設定私人頻道與授權。

## 建議資料流程

```text
裝置 A／協作者儲存資料
  → 雲端交易完成資料異動
  → 資料庫發出變更通知
  → 裝置 B 收到通知
  → 合併短時間通知並排入同步
  → 透過既有同步流程讀取雲端並處理本機待送變更
  → 更新本機快取
  → 目前模組重新查詢資料，保留未儲存草稿
```

- 通知由資料庫異動路徑產生，避免只在前端發送而漏掉其他寫入入口。
- 通知應對應成功提交的異動，回滾交易不應產生可見的成功更新訊號。
- payload 只包含必要的識別資訊或版本，不傳整份私人資料或行程文件。
- 收到通知不直接覆寫本機資料；以受授權的同步查詢結果為準。
- 先確認個人與共享資料的同步範圍，避免將私人同步能力誤當成已支援所有共享異動。

## 私人頻道與授權

### 帳號頻道

通知同一帳號的其他裝置有個人資料更新。
訂閱者只能接收自己帳號的頻道，不因知道另一個帳號 ID 就能訂閱。

### 行程頻道

通知目前有權限的成員，共享行程內容已更新。
訂閱授權必須驗證實際成員資格與權限，不以頻道名稱或前端按鈕判斷。

### 權限變動

接受邀請、新增成員、撤權、退出及結束協作也必須納入設計。
只訂閱目前已知的行程頻道，不足以發現新加入的行程。
已被撤權的人也不能只靠原行程頻道收到通知：
實作前須設計帳號層級的權限失效通知或受控重新驗證路徑，
並確認既有連線的授權更新／重新訂閱行為。

登出、切換帳號與權限變更時清除舊訂閱，防止舊事件更新新帳號畫面。
真正資料存取仍由資料庫 RLS／RPC 權限驗證保護。

## 同步排程與可靠性

### 合併通知

一次操作可能影響多筆資料。短時間事件應合併為一次同步，
並設定最大等待時間，避免持續事件讓同步一直被延後。
合併時距需實測後決定，不在本評估承諾固定值。

### 防止重疊與自觸發循環

- 同一工作區同時只執行一輪同步，沿用既有鎖與帳號 guard。
- 同步途中收到通知，記錄需再檢查，完成後合併補跑。
- 本機上傳也可能收到自己的通知；不能因此無限同步。
- 重複、延遲或順序不同的通知不應導致資料倒退或重複寫入。
- 判斷是否有新資料應依可靠的版本／增量游標，不依賴通知順序。

### 斷線與恢復

通知不是完整、可靠的離線事件紀錄，手機休眠或網路中斷可能漏訊息。

- 訂閱建立／重連後，安排受控的補同步，縮小初次讀取與開始監聽之間的空窗。
- 回到前景或網路恢復時重新確認資料。
- 視實測需要保留低頻前景輪詢；隱藏分頁不持續高頻查詢。
- 網路錯誤採逐步延長重試間隔，避免失敗風暴。
- 不以每 2～3 秒完整下載全部資料作為預設替代方案。

## 使用者體驗與各資料模式

- **單機模式**：不建立雲端即時訂閱，不增加同步等待。
- **混合／自動同步模式**：收到通知排入既有同步，保留本機待送資料與衝突處理。
- **混合／手動同步模式**：不擅自改為自動上傳；是否僅標示有更新或允許安全下載，
  須在實作前確認產品行為與既有引擎限制。
- **直接雲端模式**：通知應使相關查詢失效並重新讀取，不假裝經過本機 outbox。

背景更新不整頁重載、不反覆顯示全頁 loading，也不在每次通知顯示同步 toast。
目前編輯的未儲存草稿不得被遠端資料直接覆蓋；
需要時延後畫面更新或提示有新版本，衝突由既有機制明確處理。
監聽成功、同步到本機，以及畫面資料更新是不同階段，必須逐一接線。

## 建議實作階段

1. **盤點與設計**：確認所有寫入入口、個人／共享同步範圍、
   通知觸發位置、RLS、頻道授權、方案額度與手動模式行為。
2. **最小通知流程**：私人帳號／行程頻道、資料庫事件、共用同步排程及訂閱清理。
   如需雲端 migration，另行取得批准後才安裝。
3. **恢復與 UX**：重連補同步、事件合併、同步途中再排程、草稿與衝突保護、
   通知到快取再到各模組的更新接線。
4. **驗證與觀察**：在批准的測試環境驗證雙裝置與多人情境，再確認部署。

## 驗收情境

- 同帳號 A 裝置更新個人資料，B 裝置不重新整理即可看見最新內容。
- 協作者修改共享行程，擁有者／其他成員取得授權內的最新內容。
- 新接受邀請可被發現；撤權、退出與結束協作後正確更新存取狀態。
- 無關帳號不能訂閱或取得其他帳號／行程資料。
- 多筆連動異動不產生等量同步；同步中通知不啟動並行同步。
- 自己上傳引發通知不造成同步循環。
- 斷線期間異動，在重連或回到前景後能透過補同步收斂。
- 帳號切換後舊事件不污染新帳號；跨分頁同步仍遵守鎖定規則。
- 編輯中收到更新不清空草稿；衝突不默默覆蓋任一方資料。
- 確認各模組真的刷新資料，而非只有雲端或本機快取已更新。
- 手動與單機模式不出現未經同意的自動上傳。
