# 日本全國 OSM 可行性初評

後續正式整合狀態、決策與交付驗收集中見 [日本全國整合紀錄](osm-japan-rollout.md)；本文件保留先前階段的歷史量測。

評估日期：2026-10-25（Asia/Taipei）。初評階段僅做程式審查、現有檔案／SQLite 唯讀盤點與上游資料查核；當時尚未下載日本 PBF 或建置日本產物。後續下載及實驗結果依序記錄於本文末尾，目前未修改正式服務或路由實作。

## 結論與證據範圍

現有 SQLite 按需路由適合作為日本全國的第一個實驗基線，但目前無法保證全國建置成功、服務記憶體、搜尋速度或長途路由可用。應先分階段驗證資料建置，再驗證服務，最後決定是否上線。沒有證據支持重做常駐陣列路由。

`routing-performance.md` 的約 30–32 MiB 與約 0.03–0.25 秒是特定台灣工作負載，並非全國圖資的資源上限。`osm-taiwan-implementation.md` 仍含早期全圖載入、台北至高雄約 9 秒等歷史紀錄；不能視為目前約 2 秒搜尋預算下的驗收結果。

## 建置流程與主要風險

現行順序為下載／MD5 → 顯示資料 → 地點擷取 → 路網／連通索引 → 搜尋索引 → 圖磚 → manifest，各腳本以子程序依序執行。峰值應按各階段量測，而非把不同階段的 RAM 相加。

| 階段與程式 | 目前行為 | 全國規模風險 |
| --- | --- | --- |
| `prepare-dataset.py` | `flex_mem` 座標索引；同時保留道路節點字典、ways、道路／水域 features、海岸幾何；最後 `unary_union`／`polygonize` | 大量 Python 物件與 GEOS 幾何同時存活；輸出 `nodes` 陣列還會增加暫時配置。這是優先量測的建置風險 |
| `extract-places.py` | 多次掃描 PBF，保存 relation 成員集合、locations、relations 與全部 places；最後整份 `json.dumps`／`write_text` | 磁碟搜尋只降低服務用量，未消除擷取時的 catalog、座標及序列化峰值 |
| `build-routing.py` | 第一輪用 `Counter` 保存所有可通行道路節點引用與端點集合；第二輪搭配 `flex_mem` 寫 SQLite | 全圖 Python 計數資料仍存在，且節點計數規模可遠大於最後保留的路網節點 |
| `routing_index.py` | 所有路網 ID 到連續序號的 Python 字典，以及三組 union-find parent／rank、outgoing | 是離線 O(N+E) 工作，並非固定記憶體；既有陣列僅供連通分量準備，不是已撤回的常駐陣列路由 |
| `disk_search.py` 準備 | 一筆筆解析 JSON、寫入 SQLite | 不載入整份 catalog，但寫入／臨時磁碟空間與耗時仍隨資料增加 |
| `build-tiles.py` | 讀完整 land JSON；tippecanoe 限 2 threads、zoom 5–14；取消 feature／tile size 上限；最後 `read_bytes()` 算 hash | 幾何、排序暫存、個別圖磚大小與最終 MBTiles 大小都須量測；末尾 hash 會把整份 MBTiles 配置到 RAM |

pyosmium 的座標儲存是幾何建置的另一份資料結構，見[官方幾何文件](https://docs.osmcode.org/pyosmium/latest/user_manual/03-Working-with-Geometries/)。不可只計算 Python 容器而忽略原生記憶體。

現有主機是否足以跑原封不動的建置仍未知。若需先準備另一台實驗建置機，可將 16–32 GiB RAM 加 SSD 當作初始採購／租用評估範圍，但這不是已量測需求或成功保證；先做地圖樣本會比直接決定硬體更有依據。正式服務規格應由另一組服務量測決定。

## 服務與長途限制

- `compact_routing.py` 名稱雖含 Compact，目前實際是 SQLite 按需讀取。每個模式正反向鄰接各快取 4,096 節點，共用座標／分量快取 32,768 筆。全國圖變大不代表 HTTP 程序載入全圖，但搜尋狀態、路線幾何、成功結果快取及多 dataset 共存仍占記憶體。
- 每段共用約 2 秒搜尋預算，每 128 次迴圈檢查，展開數超過 50,000 或兩端狀態合計超過 100,000 會中止；不是整個 HTTP 請求的硬性 2 秒保證。吸附、磁碟等待、幾何重建、回應序列化另需時間，最多 10 個地點也會形成 9 段計算。
- 弱連通分量只能快速排除不可能的候選，不保證有向可達或長距離能在預算內完成。日本全國連通大分量可能增加搜尋範圍，須實測東京至大阪等案例。
- 全服務只有一個路由名額，跨台灣／沖繩／未來日本共用；忙碌時其他路由直接 503。增加 RAM 或 worker 不能在未評估前視為解法。
- 只匯入允許的 `highway` ways，未建置 ferry／鐵路連接；旅客能搭船或火車到達不表示道路圖可達。跨海測試要依實際交通方式的道路連通判定，不把所有跨島案例都預設成功或失敗。無完整轉向限制、條件式通行與即時交通，時間為靜態估計。
- 搜尋 SQL 使用 `instr` 掃描名稱，再用視窗函數去重、計算總筆數與排名；`LIMIT 30` 不表示只掃描 30 筆。日本常見單字查詢、無結果與多語名稱必須測冷暖延遲、RSS、暫存磁碟及並行影響。
- 圖磚 runtime hash 已採串流，但第一次開啟 dataset 仍須讀完 MBTiles；該初始化持有全域 dataset 鎖，也需要納入首次使用測試。

## 新增第三區前必須處理的接點

1. 多個建置 CLI 的 choices 只允許台灣／沖繩，下載來源也只有台灣／九州分支；現在不能直接執行 `--dataset japan`。
2. `server.py`、setup 及啟動前準備只有台灣啟用磁碟地點搜尋。日本必須明確使用相同磁碟路徑，避免落入全量 `PlaceSearch(json.loads(...))`。既有沖繩別名實作保留。
3. `shared/geo/osm-datasets.json` 需新增有來源依據的 coverage，不能把全國外框全部當作有效陸地；現有 coverage 產製腳本固定台灣。應確認小島、沿岸容差、海岸不閉合及涵蓋判定成本。
4. `localOsmRegionId()` 對所有非沖繩 dataset 都回傳台灣 ID，直接新增日本會碰撞，需為第三區建立獨立且穩定的 ID。
5. 全國 coverage 會與沖繩重疊。`datasetForCoordinate()` 目前依 manifest 順序取第一個符合者，僅靠座標不能表達使用者選定的 dataset。需定義新地點自動歸屬及公開／共享行程的政策，並保留既有沖繩資料身分。
6. 同步、匯入、備份與雲端 dataset／coverage 驗證也需後續專項審查。本輪未更動或驗證資料庫。
7. 啟動會掃描所有 `*-routing.sqlite` 並準備索引。實驗產物須放在服務資料夾外，避免未完成的日本實驗影響既有服務啟動。
8. 單檔原子替換不等於整批原子發布。全國正式更新需 staging、完整驗證及批次切換，避免混用不同日期的圖磚／地點／路網。

## 建議實驗順序與通過條件

1. **隔離地圖樣本**：先以關東或關西等官方地圖檔量測；官方下載頁提供分區連結。實驗只在獨立目錄及程序執行，先調整實驗入口的來源、輸出與 dataset 配置，不先改正式選單／雲端。樣本結果只能驗證流程與發現瓶頸，不能證明全國長途成功。
2. **各階段資源紀錄**：固定 PBF 日期、checksum、程式 commit、套件與硬體。用 `/usr/bin/time -v` 記錄 wall time、max RSS，另採樣可用 RAM、工作目錄及 `/tmp` 用量；階段獨立執行，記錄節點／路段／地點數與產物大小。設定程序記憶體及時間上限並保留主服務空間；接近限額即停止，不能靠 OOM 後猜測需求。
3. **全國路網先行**：樣本可行後，先只建全國路網及連通索引，確認 `integrity_check`、端點完整性、三模式方向與連通分量，再跑真實路線。暫緩昂貴圖磚與 catalog，及早確認核心長途能力。若原有建置容器先超出資源，優先考慮串流／磁碟中間資料、座標索引儲存方式及串流 hash，保留 SQLite 路由基線。
4. **路由矩陣**：每種模式測東京／大阪／札幌／那霸市區、郊區與山區，並涵蓋約 10／50／100 公里、東京至名古屋／大阪、同分量有向難例、確定不連通離島、重試失敗、模式切換與 10 地點行程。距離是測試分級，實際道路距離須記錄。分開統計成功、超時／範圍上限、不連通及吸附失敗，並測幾何與距離／時間合理性。
5. **完整搜尋與底圖**：路網結果可接受後再建完整 catalog／搜尋索引與圖磚，測「東京」「駅」「店」、具體 POI、多語別名與無結果查詢；檢查多地高低 zoom、海岸／小島與最大圖磚大小。記錄建置與冷啟動耗時。
6. **服務驗收**：冷程序／首次 query、暖機查詢至少各 20 組，公布 median／p95／最大值與錯誤比例；區分程序冷啟動與真正磁碟冷快取，勿在共用主機清全機 page cache。測路由＋搜尋＋圖磚、三區共存與長時間 RSS／磁碟使用。沿用既有服務且確保台灣／沖繩回歸通過。
7. **決策**：建置必須在實際資源限額內完成並保有餘裕；長途需求案例須逐項通過原有限制，不能靠提高上限後宣稱原實作通過。短途可用但長途頻繁達限時，只能承諾已驗證範圍；再另案比較階層式路由或專用引擎。服務延遲與容量目標需在正式驗收前固定，現階段尚無日本成績。

本輪產出為上述初評，沒有日本測試結果，也沒有可對外承諾的日本 RAM、建置時間或路由成功率。

### 實驗資源界線

每個建置實驗以獨立低優先序程序執行，設定 RSS 採樣上限 5,120 MiB、`RLIMIT_AS` 虛擬位址空間上限 7 GiB、主機 available RAM 保留 2,048 MiB，以及 900 秒時間限制。每秒採樣，因此 RSS／主機餘裕是監控門檻，並非核心保證的即時硬限制；`RLIMIT_AS` 才是程序的位址空間硬限制。

RSS 是實際常駐記憶體；虛擬位址空間含映射與保留配置，兩者不可互換。未為了測出極限而取消保護或等候主機 OOM。

- 沒有執行第二輪座標處理、路網寫入與 SQL 索引建立，也未量測完整路由初始化或 HTTP 查詢。
